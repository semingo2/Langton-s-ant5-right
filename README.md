# 2匹のラングトンのアリ — C++解析＋Web UI

2匹のアリを同時に動かし、104歩周期のハイウェイと相対状態ハッシュによるループを解析するアプリです。シミュレーション／解析はC++17、画面はHTML・CSS・JavaScriptです。

## 機能

- 蟻1（赤）・蟻2（青）のシミュレーション
- 実行／一時停止、1歩・100歩・1,000歩進める操作、速度変更
- マスの大きさ変更、蟻どうしの間隔・向き変更、盤面スクロール／ドラッグ
- 各蟻について104歩周期の反復を20周期分確認するハイウェイ検出
- ハイウェイ開始推定歩数・検出確認歩数の表示
- 黒マス総数、一度でも通ったマス数、ハイウェイ経路のマス数、ハイウェイ経路以外の黒マス数
- 蟻1を原点とする相対座標・両方の向き・相対盤面ハッシュによるループ検出

## ローカルで実行する（Windows）

g++（MinGW-w64 / MSYS2など）を用意して、プロジェクトフォルダーで実行します。

```bat
g++ -std=c++17 -O2 -pthread main.cpp -lws2_32 -o langtons_ant_server.exe
langtons_ant_server.exe
```

ブラウザーで `http://127.0.0.1:8080` を開きます。

## GitHubにコードを公開し、Webサイトとして動かす

**GitHub Pagesだけでは、このC++サーバーは実行できません。** GitHub Pagesは静的ファイルを配信する仕組みで、実行中のC++ HTTPサーバーを起動しないためです。

このリポジトリにはRenderでC++サーバーごとホストするための `Dockerfile` と `render.yaml` を入れています。GitHubにはソースコードを公開し、Renderがそのリポジトリからビルドして公開サイトを動かす構成です。

1. GitHubで新しいリポジトリを作成します。
2. このフォルダー内のファイルをすべてリポジトリのルートにアップロードし、コミットします。
3. Renderにサインインし、GitHubアカウントを連携します。
4. Renderで **New → Blueprint** を選び、このリポジトリを指定します。`render.yaml` の内容を確認してデプロイします。
5. デプロイが成功すると、Renderが発行する `onrender.com` のURLでアクセスできます。

`HOST=0.0.0.0` と `PORT` はホスティング環境用です。ローカル実行時は既定で `127.0.0.1:8080` に待ち受けます。

## 公開時の注意

- **盤面はブラウザーセッションごとに独立しています。** 最初のアクセス時にサーバーがランダムなセッションIDをCookieに設定し、そのIDに対応するC++ `Simulation` インスタンスを割り当てます。別のブラウザーや別のブラウザープロファイルは別の盤面・歩数・解析履歴を持ちます。同じブラウザープロファイル内のタブは同じCookieを使うため、同じ盤面を共有します。
- セッションは12時間操作がないとサーバーから削除されます。サーバーが再起動した場合も、メモリ上の盤面・解析履歴はリセットされます。CookieにはセッションIDだけを保存し、盤面データはサーバーのメモリで管理します。
- 無料ホスティングには稼働時間・スリープ・処理性能などの制限がある場合があります。公開前にRender側の現在のプラン条件を確認してください。
- 104歩周期の候補を20周期分確認してから開始歩数を推定します。ループ判定は独立した2つの64-bitハッシュを含む状態比較であり、ハッシュ衝突の可能性は理論上ゼロではありません。
- 公開版では、利用者間で盤面が混ざらないようにCookieベースのセッション管理を追加しました。シミュレーションのルール、操作、ハイウェイ検出とループ検出のロジックは維持しています。

## 軽量化について

この版ではシミュレーション規則・検出条件・表示項目を維持したまま、内部の保存方法と画面通信を軽量化しています。

- 黒マスとハイウェイマスの座標を別々のフルセットで重複保持せず、行ごとの集合を共通の参照元にします。
- ハイウェイ検出のスナップショットは直近313状態、折れ曲がり履歴は各蟻312歩分だけ保持します。候補発見後だけ経路候補を一時保存し、20周期の確定に必要な分を記録します。両方のハイウェイ確定後はこの履歴を解放します。
- 折れ曲がり履歴の区間ハッシュと累乗配列を廃止し、104歩の小さな区間を直接比較します。
- ループ検出キーを2つの64-bit指紋へ圧縮しました。ハッシュ方式のため、衝突確率を完全にゼロとはできません。
- 座標累乗のキャッシュは蟻1を原点にした相対座標でのみ使い、各軸2,048個までに制限します。
- 画面更新では、歩数・解析結果と表示範囲のマス情報を1回のHTTP応答にまとめ、連続実行中の更新頻度をおよそ20回/秒に制限します。設定した歩数/秒をもとに各バッチの歩数を計算します。

### メモリに関する大事な制約

ループを正確に検出するには、既知の状態履歴を記録し続ける必要があるため、`seenStates` はループが見つかるまで増えます。また、一度でも通ったマスと黒マスの現在状態も保持します。これらは研究上の計測・検出要件を保つためのデータで、これを完全に上限固定にすると検出精度や計測結果を変える可能性があります。
